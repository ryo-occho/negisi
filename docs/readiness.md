# 利用開始の準備と動作検証

## 現在の到達点

希望シフトのログイン・入力・保存・提出・共有まで実装済みです。確定シフトの割り当て・調整・公開は対象外です。
Supabase 接続の PR #8 は `develop` にマージ済みです。本番の `main` へのリリースはまだ行っていません。

2026-10-24 にクラウドを読み取り確認した結果、マイグレーション2件は適用済みで、Auth ユーザー・スタッフ・対象期間は各0件でした。クラウドの公開サインアップは有効（`disable_signup=false`）です。今回、クラウド設定の変更や実スタッフ登録は行っていません。

## 実スタッフの利用開始前

1. Supabase Dashboard の Authentication 設定で「Allow new users to sign up」を無効化します。登録済みユーザーのメール・パスワードログインは有効にします。
2. [スタッフ登録手順](supabase-connection.md#スタッフ登録) に従い、Auth ユーザーをメール確認済みで作成します。スタッフから受け取る情報は表示名とメールアドレスです。
3. Auth の UUID と同じ ID で `staff` に表示名と `active=true` を登録します。Auth の作成だけでは利用できません。
4. 初期パスワードは本人だけが受け取れる経路で渡します。ソースコード、Issue、PR、共有チャットには記載しません。パスワード再設定は当面 Dashboard の運用で対応します。
5. 本人の端末でログインを確認します。スタッフ間でアカウントを共用しません。
6. 提出締め切りと昼・夜の時間帯、期間を作成する担当者を店舗内で決めます。アプリに管理者ロールはなく、全スタッフが期間を作成できます。

## ローカル検証

Node.js 22 と Docker Desktop を使用します。クラウドのスタッフ情報・パスワード・秘密キーを検証データに使いません。

```sh
npm ci
npm run lint
npm run format:check
npm run typecheck
npm run build
npm run db:start
npm run test:db
```

DB テストは2ファイル・28項目です。各テストはトランザクションをロールバックします。

画面から認証・Data API まで検証する場合、DB に加えて Auth・REST・API ゲートウェイが必要です。DB だけが起動済みの場合は、先に `npx supabase stop --project-id negisi` でこのプロジェクトだけ停止してから、以下を実行します。`--no-backup` は付けず、既存のローカルデータを保持します。

```sh
npx supabase start -x realtime,storage-api,imgproxy,mailpit,postgres-meta,studio,edge-runtime,logflare,vector,supavisor
```

ローカル API は `http://127.0.0.1:55321`、DB は55322です。`npx supabase status -o json` の出力にはローカルの秘密キーも含まれるため、共有・コミットしません。
既存の `.env.local` を上書きせずローカルに接続する場合、PowerShell では同じターミナルで次のように起動できます。

```powershell
$localStatus = (& npx.cmd supabase status -o json | ConvertFrom-Json)
$env:NEXT_PUBLIC_SUPABASE_URL = $localStatus.API_URL
$env:NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY = $localStatus.PUBLISHABLE_KEY
npm.cmd run dev -- --hostname 127.0.0.1 --port 3100
```

環境変数はこのターミナルのプロセスに設定されます。検証終了後はターミナルを閉じます。
ローカル Auth Admin API などの信頼できる経路で架空の検証ユーザーを用意し、その UUID でローカルの `staff` に登録します。service role はセットアップ処理のみで使い、ブラウザーには渡しません。スタッフA・Bに加え、`staff` に登録しない Auth ユーザーを用意すると権限境界も確認できます。

| 操作                                          | 確認する結果                                                 |
| --------------------------------------------- | ------------------------------------------------------------ |
| スタッフAでログインし、将来の半月の受付を作成 | 日本時間の締め切りと対象期間が保存される                     |
| 昼・夜・どちらも可を選び、下書き保存          | DB に希望が保存され、提出日時は null                         |
| 再読み込みし、同じ対象期間を選択              | 保存した希望が復元される                                     |
| 希望を提出                                    | DB に提出日時が保存される                                    |
| 編集後、期間を移動しようとしてキャンセル      | 警告が出て、元の期間と入力が保持される                       |
| 編集後に下書き保存し、再提出                  | 下書きで未提出に戻り、再提出で提出済みになる                 |
| スタッフBで「みんなの希望」を開く             | Aの希望と提出状況が表示される                                |
| Bが何も選ばず提出                             | 全日出勤不可でも提出済みになる                               |
| ローカルDBで締め切りを過去に変更              | 入力・提出が無効になり、RPC の保存も拒否される               |
| ローカルDBで A の `active` を false にする    | 既存セッションでも利用を拒否される                           |
| ログアウト後、Auth だけのユーザーでログイン   | スタッフ未登録の案内が表示される                             |
| 未ログインで Data API にアクセス              | スタッフ情報にアクセスできない                               |
| 幅390pxの画面で操作                           | ページ全体が横にはみ出さず、共有表の内側で横スクロールできる |

検証後は作成した検証用の希望・提出状況・期間・スタッフ・Auth ユーザーだけを削除します。既存のローカルデータは削除しません。`npx supabase stop --project-id negisi` でこのプロジェクトだけ停止できます。

## Preview と PR

1. 最新の `develop` から作った `feature/*` ブランチで、上記の検証結果と未対応事項を記載して `develop` 向け PR を作成します。
2. GitHub Actions の ESLint / Prettier、型チェック / Next.js ビルド、対象となる DB テストを確認します。CI はクラウドの認証情報を使いません。
3. Vercel の対象チーム・プロジェクト・コミットが PR と一致し、Preview が Ready であることを確認します。
4. Preview のスマートフォン表示、ログイン画面、Auth への接続を確認します。Vercel Authentication がある場合は、既存の認証や一時 OIDC ヘッダーでアクセスし、保護設定を無効化しません。トークンは PR に記載しません。
5. 実スタッフ未登録の Preview では、ログイン後の業務操作は検証できません。ローカルでの業務操作検証と区別して結果を記載します。

本番への公開は、スタッフ登録・公開サインアップ無効化・運用ルールの確認後に、別途承認を得て `develop → main` の PR で進めます。
